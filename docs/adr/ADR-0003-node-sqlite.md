# ADR-0003: Журнал действий сервера — node:sqlite вместо better-sqlite3

- Статус: принято (2026-09-18)
- Контекст: сервер (apps/server) хранит идемпотентный журнал ScoreAction + снапшоты проекций. Требования: встраиваемое хранилище (клуб ставит один процесс), транзакции, атомарный UNIQUE(tournament_id, action_id), воспроизводимость в CI.

## Решение
`node:sqlite` (встроенный модуль Node ≥ 22, DatabaseSync). Схема — apps/server/src/store.ts.

## Причины
1. **better-sqlite3 недоступен в нашей среде**: требует node-gyp + C/C++ toolchain и заголовки Node; в CI-песочнице сборка native-модуля падает (проверено фазой 1). External-baseline регресс блокирует «внешнюю» зависимость без сильной причины.
2. node:sqlite покрывает сценарий: WAL-режим для параллельных читателей SSE, подготовленные выражения, `INSERT OR IGNORE` — идемпотентность одной строкой SQL.
3. Ноль новых рантайм-зависимостей → бюджет артефактов и reproducible install (`npm ci` без network-компиляций).

## Рассмотренные альтернативы
- **better-sqlite3** — быстрее на больших батчах, но нативная сборка; отложено: при переходе клуба на long-running прод-сервер вернуться к вопросу (порог: >2 тыс. действий/сек).
- **JSONL-файл** — проще, но нет UNIQUE-констрейнта и точечного чтения; дедупликация в памяти при рестарте — O(N) и риск гонок.
- **Postgres** — избыточен для локального клуба (еще один сервис, бэкапы); оставлено как путь мульти-клуба (ARCHITECTURE §12 tenant).

## Последствия
- Experimental-warning Node при старте (`SQLite is an experimental feature`) — подавляется флагом при необходимости; API стабилизирован в Node 22.5+ runtime-wise.
- Лимиты: журнал одного турнира ≈ 144×18×8 ≈ 21K строк/день — годы работы без компактификации.
- Тесты серверных путей — через DatabaseSync на tmp-файлах (unit в vitest без специального окружения).
